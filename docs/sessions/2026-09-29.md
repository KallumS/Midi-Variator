# Session log - 2026-09-29

The first session. The repo started empty but for its licence.

## What was asked

A ReaScript or JSFX that makes tiny variations of imported MIDI clips, from
Nordic Noir, where each repeated melody, phrase or bar changes a small thing.
Variations in notes, intervals, timings, lengths, velocities and anything
else; notes added or taken away. The changes must be small, and **every
change must refer to the original clip**, so twenty variations in a row
still resemble it. It should work on melodies, chords and everything in
between.

ScaleView-for-Reaper, Starting-Blocks and Midi-Suggester were pointed to as
prior work, with the REAPER user guide, API reference, JSFX reference and a
music-theory library uploaded.

## What was built

A Lua ReaScript ([0001](../decisions/0001-a-reascript-not-a-jsfx.md)) laid
out like Midi Suggester: pure music files, a REAPER layer, a ReaImGui window,
and tests for each against mocks. Its test runner (lupa fallback) and check
helper were copied across, and its mock REAPER extended.

- `mv_theory` - Midi Suggester's keys and key finder, copied unchanged.
- `mv_vary` - the engine: fifteen moves in five kinds, feel, a budget, a
  series memory, and encoding the original into an item.
- `mv_place` - reading items (trims, loops), making variations as new items
  ([0002](../decisions/0002-variations-are-new-items.md)) after the original,
  rewriting in place when safe ([0005](../decisions/0005-rewrite-in-place-only-when-safe.md)),
  putting the original back.
- The window: source, what may change, variations - with a preview roll, the
  list of changes, and arrows through the batch.

## What the tests found

**Keep the first and last notes was broken by rolls.** Rolling the first
chord moved its notes up to 0.19 of a beat. Rolls now respect protection.

**The lengths feel made chords grind.** A held G major chord lengthened by
a few percent rang on into the next chord, its B against the new chord's C.
Lengthening now stops at the next moment.

**Chord fills made mud.** "Filling out" a Cmaj7 doubled its B low, against
the C bass - eight beats of minor ninth. Fills now pass the clash guard.

**The key was wrong for a piece ending on a half cadence.** A minor ending
on E major read as E minor, and steps offered F# and G# where they did not
belong. Decision [0004](../decisions/0004-the-scale-is-the-seven-notes-used.md):
the scale is the seven-note set the music covers.

**Tidying "fixed" the original.** The arpeggio fixture overlaps same-pitch
notes on purpose; a variation at amount 0 trimmed them. `tidy` now leaves
the original's own overlaps as written.

**Drum variations only ever removed hi-hats**, and "tied two F#2s". Drums
now have names, a ghost-note move, and no ties.

**The pickup move was slow on long pieces.** It asked, for every moment,
where the last note before it ended: 0.84s for four variations of 2,000
notes. One sweep: 0.12s.

## Proving the tests bite

Each rule was broken on purpose and the suite watched. Four mutations
passed at first, and each gap now has a test that fails without the rule:
removing the change cap (never reached - a two-note test now reaches it),
removing the series memory entirely (only half of it had been removed),
ignoring the item's lead when writing (no test wrote an item starting
mid-bar), and leaving a half-made batch after a refusal (the refusal test
had nothing made before it).

## Not done

Not run in REAPER - the window has only been driven by a mocked ReaImGui.
The ReaPack index points at this branch's commit and works once merged.

## Later: the scale step (1.1)

Asked: is it scale-aware, and does it keep notes in the detected scale? It
did (decision 0004), with three gaps named: a pentatonic tune could gain
notes outside the pentatonic, one scale per clip, and the scale could not be
seen or changed. The user asked for a key/scale picker - "the user might
want to pivot to a different scale with the variations" - and a switch to
stay in the original's notes that bypasses detection.

Built ([0006](../decisions/0006-pick-a-scale-and-pivot.md)):

- A **Scale** step: 18 roots, ScaleView's 16 scales (copied unchanged with
  their spellings), *Back to what it heard*.
- **The pivot**: *Bring the original into this scale*, on by default, fits
  the original by nearest note (same letter on a tie) before varying it. The
  window lists what moves. The original kept inside is always the real one.
- **Stay in the original's notes**, which hides the picker.
- **A step is never more than a major third**, for sparse scales.
- The steps now number themselves, so drums (no Scale step) have no gap.

What went wrong on the way:

- `analyse` never received the pick: the edit to its comment block did not
  match, so neither did the signature change beside it. Caught by the first
  demo run, which found no picked scale.
- The same-letter tie-break passed its test with the rule removed: C major
  into C minor rounds down either way. A C minor to C major test (Eb -> E,
  not D) now fails without it.
- "Picked but not fitted" was guarded twice; after a pivot every note is in
  the scale, so the second guard could never matter. Removed.
- Nothing varied *in place* with a scale picked; a test now does.
- "Heard as C Major (the first item)" was wrong when the first item was
  drums; it now names the item it heard.

Still not run in REAPER.

## Later still: the first run in REAPER (1.1.1)

The user ran it in REAPER: "seems to be working well", but *Vary selected
in place* raised

    Midi Variator.lua:692: bad argument #1 to 'GetSetMediaItemInfo_String' (MediaItem expected)

The window listed the selected items, drew *Vary selected in place*, and -
after the click - went on through the same list to decide whether to draw
*Put back the original*. Varying had replaced some of those items with new
ones (pooled copies, `.mid` files and loops are replaced, decision 0005),
so the list held deleted items, and REAPER refuses those.

Why the tests missed it: the mock let a deleted item be used as if it were
still there, and no window test varied in place an item that gets replaced
(the place tests did, but never drew a frame afterwards).

Fixed three ways:

- The window reads the selection again after varying.
- The mock now refuses a deleted item or take in every call but
  `ValidatePtr2`, as REAPER does - every suite passes under it, so nothing
  else held a deleted item.
- A window test varies two pooled copies and a `.mid`-file item in place,
  twice, and puts them back. It fails with the user's exact message
  without the fix.

It also showed a second bug: when the items being shown were replaced, the
window re-read them *after* writing "Varied 3 items in place", and
re-reading clears the status line, so the message never appeared. The
order is swapped.

## Later again: chord quality (1.2)

Asked: when it detects a chord, could a variation change its quality -
"a 7th chord ... into an 11th, or diminished"? While it was being built the
user added that ScaleView Pro is the definitive chord detector (ScaleView a
simplified version).

Built ([0007](../decisions/0007-chord-quality-by-scaleview-pro.md)):

- `mv_theory` is now the whole of `ms_theory`, unchanged, which brings
  ScaleView Pro's chord reader - checked line for line against
  `ScaleView Pro.lua` at `e31a6e8`.
- A `quality` move: thirty rules, each one step to a neighbouring quality
  (add, move or drop one note). Bass never moves; repeated chords change
  as one; in the scale unless *Chord changes may leave the scale*.
- "Chords" split into *Chord voicing* and *Chord quality*.

What went wrong on the way:

- `analyse` looked up the scale table before the file had defined it - a
  local declared further down. Caught by the window test.
- Added notes went in low, next to the bass. Now as high inside the chord
  as they fit.
- The clash test failed on Cmaj7 and Fmaj7: its major seventh is a
  "grinding" interval. That is chord colour, asked for. The test now
  ignores notes struck together where a quality changed, and a new test
  holds that a changed chord grinds against nothing outside it.
- The repeated-chord test looked only forward from the strike that was
  picked; a run can extend backwards too. The test was wrong, not the
  code.
- Test expectations had to learn ScaleView Pro's vocabulary: "G7(13)",
  not "G13".

Each of the five chord-quality rules was broken on purpose and the suite
failed every time. Not yet run in REAPER.
